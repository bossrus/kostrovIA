Мини-CRM «Объекты и задачи» — React, TypeScript, Vite и облачный Supabase.

Приложение поддерживает вход по email и паролю, объекты, задачи, назначения, пять статусов и историю. Все постановщики видят общие объекты и задачи, могут редактировать и удалять записи друг друга, принимать и возвращать работу. Редактировать и переназначать задачи можно в любом статусе, включая «Принята»; статус при сохранении не меняется. Исполнитель видит свои назначения и связанные объекты, меняет только разрешённые статусы своих задач. У пользователя ровно одна роль: постановщик или исполнитель.

## Обновление существующей базы

Для проекта с исходной схемой выполните в Supabase SQL Editor `supabase/migrations/202611050003_shared_managers.sql`, затем `supabase/migrations/202611050004_project_owner_names.sql` от имени postgres. Старые миграции повторять не нужно. Затем обновите приложение и выполните `npm run test:security`. На текущем облачном проекте обе новые миграции применены 5 ноября 2026 года.

Миграция 003 атомарно обновляет RPC, RLS-помощники и триггер, добавляет ограничение ровно одной роли. Для существующей demo `mixed@kostrov.demo` остаётся постановщиком, а его неудалённые назначения передаются `executor1@kostrov.demo`. Авторы, объекты, даты, статусы и история задач сохраняются; версии переназначенных задач увеличиваются. Произвольные смешанные профили автоматически не преобразуются: при их наличии миграция откатывается с пояснением, чтобы администратор явно выбрал роли и исполнителей. Миграция 004 открывает исполнителю имя создателя доступного объекта, даже если его задачу создал другой постановщик. В списке объектов каждая карточка показывает имя постановщика.

Продакшен: [kostrov.netlify.app](https://kostrov.netlify.app). Исходники: [bossrus/kostrovIA](https://github.com/bossrus/kostrovIA). Netlify собирает production из ветки `main`: команда `npm run build`, каталог `dist`; публичные переменные Supabase настроены в Netlify.

## Запуск

Нужен Node.js 22.12+ или 24 LTS.

```sh
npm ci
```

Скопируйте `.env.example` в `.env.local`, укажите URL Supabase и **publishable key** либо legacy **anon key**. У текущей локальной копии `.env.local` уже заполнен. Публичный ключ разрешено использовать в браузере: он не обходит RLS. Никогда не указывайте здесь `service_role`, secret key или пароль базы.

```sh
npm run dev
```

Откройте адрес, напечатанный Vite, обычно `http://127.0.0.1:5173`. Для production-сборки:

```sh
npm run build
npm run preview
```

Готовая статическая сборка находится в `dist`. Для Vercel или Netlify укажите команду `npm run build`, каталог `dist` и обе переменные `VITE_SUPABASE_*` до сборки. Используется `HashRouter`, поэтому переписывание маршрутов на сервере не требуется. Для GitHub Pages также настройте `base` в Vite под путь репозитория.

## База с нуля

1. Создайте Supabase-проект. Выполните в SQL Editor все четыре файла `supabase/migrations/` по порядку имени от имени postgres. Первая миграция предназначена для пустой базы; повторно выполнять её не нужно.
2. В Authentication → Sign In / Providers выключите **Allow new users to sign up**. Anonymous sign-ins должны оставаться выключенными, Email — включённым.
3. В Authentication → Users → Add user → Create new user создайте `manager@kostrov.demo`, `executor1@kostrov.demo`, `executor2@kostrov.demo`, `mixed@kostrov.demo`. Последний email — исторический логин второго постановщика, совмещения ролей больше нет. Включите Auto confirm user и задайте тестовые пароли. Реальная почта и отправка писем для демонстрации не нужны.
4. Выполните `supabase/seed.sql`: он добавит профили и роли только этим четырём существующим Auth-аккаунтам. Паролей в SQL нет.
5. Для наполнения примерами создайте локальный файл `demo-credentials.local` в формате ниже. Этот файл исключён из Git.

```json
{
  "manager": { "email": "manager@kostrov.demo", "password": "YOUR_TEST_PASSWORD" },
  "executor1": { "email": "executor1@kostrov.demo", "password": "YOUR_TEST_PASSWORD" },
  "executor2": { "email": "executor2@kostrov.demo", "password": "YOUR_TEST_PASSWORD" },
  "manager2": { "email": "mixed@kostrov.demo", "password": "YOUR_TEST_PASSWORD" }
}
```

```sh
node --env-file=.env.local scripts/demo-seed.mjs
```

Seed создаёт 3 объекта и 8 задач, проводя настоящие переходы через обычные пользовательские сессии. Все пять статусов представлены. Повторное заполнение останавливается, если уже есть видимые постановщику объекты. Текущий проект уже заполнен; запускать seed повторно не требуется. Demo-доступы текущей копии сохранены в `demo-credentials.local`; старый ключ `mixed` поддерживается скриптами как псевдоним `manager2`.

Для нового рабочего пользователя создайте Auth-аккаунт вручную и добавьте строку в `public.profiles` из SQL Editor: `id` из Auth, `display_name` и ровно одну роль: `is_manager=true, is_executor=false` либо `is_manager=false, is_executor=true`. Ограничение базы запрещает обе роли одновременно и отсутствие роли. Роли нельзя назначать через `user_metadata`: пользователь может менять эти метаданные самостоятельно. Профили и роли через клиентский API не редактируются.

## Как защищены данные

`profiles`, `projects`, `tasks`, `task_history` закрыты RLS. Для анонимного клиента нет доступа ни к строкам, ни к операциям. Авторизованному клиенту разрешён только SELECT таблиц под RLS. Любые изменения выполняют пять RPC: `save_project`, `delete_project`, `save_task`, `delete_task`, `transition_task`. Создание и редактирование объединены в двух `save_*` функциях.

Каждая изменяющая функция проверяет `auth.uid()` и защищённую роль; действия исполнителя дополнительно ограничены назначением. Автор объекта или задачи сохраняется как справочная информация и не ограничивает других постановщиков. `SECURITY DEFINER` означает выполнение операции с правами владельца функции; поэтому внутри каждой такой операции есть явная проверка полномочий и фиксированный пустой `search_path`. Помощники RLS вынесены в неэкспонируемую схему `private`, чтобы избежать взаимной рекурсии правил объектов и задач. Публичные права вызова отозваны; разрешены только нужные операции и проверки для authenticated.

Триггер `tasks_guard` дополнительно проверяет граф статусов, исполнителя и неизменность автора, объекта и даты. Триггер `tasks_audit` создаёт событие с текущим пользователем и временем базы в одной транзакции с изменением статуса. Через API нельзя добавлять, менять или удалять события истории. Логическое удаление задач сохраняет аудит в базе; история удалённой задачи из пользовательского API не читается.

Блокировка строки и `version` не дают двум запросам применить действие к одному устаревшему состоянию. Создание задачи и удаление её объекта используют общую блокировку объекта, исключая гонку с проверкой наличия задач. Редактирование названия или адреса объекта использует принцип последнего сохранения.

Пароль передаётся только в Supabase Auth по HTTPS. SDK сохраняет сессию в localStorage и обновляет JWT. Поэтому приложение должно размещаться на доверенном HTTPS-домене. Пользовательский текст выводится средствами React без `dangerouslySetInnerHTML`. Service role и административные токены не требуются для работы приложения, seed или проверок.

Архитектура RLS и использование Auth сверены с [официальной документацией Supabase](https://supabase.com/docs/guides/database/postgres/row-level-security) и [signInWithPassword](https://supabase.com/docs/reference/javascript/auth-signinwithpassword).

## Проверка безопасности

```sh
npm run test:db
```

Локальные проверки запускают изолированный PostgreSQL через PGlite без облачных доступов. Проверяются настоящие миграции, grants, RLS, RPC и триггеры: чистая установка, обновление старой demo, полный откат при нестандартной смешанной роли, общий доступ постановщиков, редактирование и переназначение во всех статусах, запреты исполнителям, сохранение статуса и истории, потеря доступа после переназначения, устаревшие версии и соответствие кнопок серверным переходам. Supabase Auth заменён минимальной тестовой схемой; настройки Auth и реальную конкурентность проверяет облачный набор.

```sh
npm run test:security
```

Тесты обращаются к реальному Supabase через publishable key и четыре пользовательские сессии. Перед созданием записей проверяются единственные роли и общая видимость постановщиков. Проверяются оба исполнителя, чтение истории, повышение роли, прямой INSERT/UPDATE/DELETE, подделка истории, редактирование и переназначение во всех статусах обоими постановщиками, обязательный комментарий, весь граф переходов, устаревшие версии и параллельная смена статуса. Сетевой сбой не засчитывается как успешный запрет. Изменяющие проверки работают с отдельным временным объектом и логически удаляют его после выполнения; его аудит остаётся в базе намеренно.
