Решения и допущения

1. Постановщик видит, создаёт и меняет только собственные объекты и задачи в них. Другие постановщики эти данные не видят. У задачи автор всегда совпадает с владельцем объекта.
2. Объект нельзя удалить, пока у него есть неудалённые задачи; кнопка удаления в таком случае скрыта. После удаления всех задач кнопка появляется. Сервер проверяет это повторно, включая гонку с созданием новой задачи. Удаление логическое: записи скрываются, а история и связи остаются в базе. Это самостоятельное решение для сохранности аудита.
3. Название, описание и назначение исполнителя меняются только в статусе «Новая». На доработке редактирование и переназначение также запрещены: задача уже была в работе. Удалять свою задачу постановщик может в любом статусе, поскольку ТЗ отдельно не ограничивает удаление.
4. Роли независимы, их можно совмещать. Смешанная роль дополнительно видит задачи, назначенные ей в чужих объектах, и эти объекты; остальные задачи там скрыты.
5. Самоназначение и приём собственной работы разрешены, если у пользователя обе роли. Разделение ответственности между разными людьми ТЗ не требует.
6. Объект, автор и дата задачи неизменяемы. Перенос задачи между объектами запрещён даже в статусе «Новая». Для переноса создают новую задачу.
7. У задачи всегда один исполнитель с соответствующей ролью; нераспределённых задач нет. Профиль создаёт и роли назначает администратор. Пользователь сам их не редактирует.
8. Постановщикам доступен общий справочник имён исполнителей для назначения. Чужие объекты, задачи, email и пароли через этот справочник не раскрываются. Исполнитель видит собственное имя и имена участников доступных ему задач. Имя действовавшего участника также сохраняется в истории.
9. Описание может быть пустым. Название объекта, адрес, название задачи и назначение обязательны. Комментарий необязателен для всех переходов, кроме возврата на доработку. Пробелы не считаются комментарием.
10. Создание задачи сохраняется первым событием истории: из отсутствующего состояния в «Новая». Редактирование текста и логическое удаление в историю статусов не входят; аудит всех полей ТЗ не требует.
11. «Принята» — конечное состояние. Отмена, повторное открытие, вложения, уведомления и сроки не добавлялись.
12. При одновременном изменении задачи один запрос проходит, второй получает предложение обновить страницу. Для названия и адреса объекта действует последнее сохранение.
13. Списки и счётчики показывают только доступные текущему пользователю записи. В карточке чужого объекта исполнитель видит прогресс только собственных задач. Время хранится в UTC и отображается в часовом поясе браузера.
14. Обновление происходит после действий и по кнопке «Обновить». Realtime, пагинация и админ-панель пользователей не реализованы: объём демонстрационной базы небольшой. После изменения назначения другой сотрудник обновляет страницу; база применяет новые права сразу, включая отклонение запросов из устаревшего интерфейса.
15. Комментарии добавлены построчно в исходники со слешами. Форматы без поддержки комментариев (стандартный JSON и lockfile) оставлены валидными. HTML, dotenv и gitignore используют обязательную синтаксическую обёртку соответствующего формата.

Статус сдачи

Приложение и база созданы локально и в указанном облачном Supabase. Демонстрация содержит два постановщика (один совмещает роли), двух отдельных исполнителей, три объекта, восемь задач и все статусы. Тестовые пароли сохранены только в игнорируемом локальном файле.

Публикация на внешнем хостинге, создание GitHub-репозитория и отправка сообщения работодателю не выполнялись. README содержит команды запуска и настройки статического хостинга. Для сообщения в hh.ru можно приложить текст из `manager-explanation.md` и этот список решений; публичную ссылку приложения и ссылку GitHub нужно добавить после публикации.
