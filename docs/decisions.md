Решения и допущения

1. По уточнению заказчика все постановщики видят общие объекты и задачи, создают задачи в любых объектах, редактируют и удаляют записи друг друга, принимают и возвращают работу. Создатель объекта и автор задачи сохраняются для справки и могут быть разными пользователями.
2. Объект нельзя удалить, пока у него есть неудалённые задачи; кнопка удаления в таком случае скрыта. После удаления всех задач кнопка появляется. Сервер проверяет это повторно, включая гонку с созданием новой задачи. Удаление логическое: записи скрываются, а история и связи остаются в базе. Это самостоятельное решение для сохранности аудита.
3. По уточнению заказчика любой постановщик меняет название, описание и исполнителя в любом статусе, включая «Принята». Исполнитель не редактирует и не переназначает задачи ни на одном этапе. При редактировании статус сохраняется; принятая задача автоматически не открывается заново. Удаление задач доступно постановщикам во всех статусах.
4. По уточнению заказчика роли взаимоисключающие. Ограничение PostgreSQL требует ровно одно истинное значение из `is_manager`, `is_executor`; тип профиля в TypeScript также исключает совмещение. Права повторно проверяются сервером.
5. Постановщику нельзя назначить исполнение задачи, поэтому самоназначение и приём собственной работы исключены. Переходы исполнителя доступны только по его назначению, а принять или вернуть работу может любой постановщик.
6. Объект, автор и дата задачи неизменяемы. Перенос задачи между объектами запрещён даже в статусе «Новая». Для переноса создают новую задачу.
7. У задачи всегда один исполнитель с соответствующей ролью; нераспределённых задач нет. Профиль создаёт и роли назначает администратор. Пользователь сам их не редактирует.
8. Постановщикам доступен общий справочник профилей: исполнители нужны для назначения, постановщики — для отображения авторов. Email и пароли не раскрываются. Исполнитель видит собственное имя, имена участников доступных ему задач и владельцев доступных объектов. Карточка объекта в списке показывает имя его постановщика. Имя действовавшего участника также сохраняется в истории.
9. Описание может быть пустым. Название объекта, адрес, название задачи и назначение обязательны. Комментарий необязателен для всех переходов, кроме возврата на доработку. Пробелы не считаются комментарием.
10. Создание задачи сохраняется первым событием истории: из отсутствующего состояния в «Новая». Редактирование текста и логическое удаление в историю статусов не входят; аудит всех полей ТЗ не требует.
11. «Принята» — конечное состояние графа переходов. Редактирование содержания и переназначение в этом статусе разрешены, но не сбрасывают его. Отмена, повторное открытие, вложения, уведомления и сроки не добавлялись.
12. При одновременном изменении задачи один запрос проходит, второй получает предложение обновить страницу. Для названия и адреса объекта действует последнее сохранение.
13. Списки и счётчики показывают только доступные текущему пользователю записи. В карточке чужого объекта исполнитель видит прогресс только собственных задач. Время хранится в UTC и отображается в часовом поясе браузера.
14. Обновление происходит после действий и по кнопке «Обновить». Realtime, пагинация и админ-панель пользователей не реализованы: объём демонстрационной базы небольшой. После изменения назначения другой сотрудник обновляет страницу; база применяет новые права сразу, включая отклонение запросов из устаревшего интерфейса.
15. Комментарии поясняют правила доступа и назначение компонентов. Форматы без поддержки комментариев (стандартный JSON и lockfile) оставлены валидными. HTML, dotenv и gitignore используют обязательную синтаксическую обёртку соответствующего формата.

Статус сдачи

Код обновлён под ответы заказчика. Миграции `202611050003_shared_managers.sql` и `202611050004_project_owner_names.sql` применены в облачном Supabase 5 ноября 2026 года. Демонстрация содержит двух постановщиков без совмещения ролей, двух исполнителей, три объекта, восемь задач и все статусы. Старый логин `mixed@kostrov.demo` сохраняется как логин второго постановщика; его неудалённые назначения переданы Ивану через защищённый RPC. Произвольные смешанные профили автоматически не преобразуются: миграция откатится и потребует выбора администратора. Тестовые пароли сохранены только в игнорируемом локальном файле.

Приложение размещено на [Netlify](https://kostrov.netlify.app), исходники — в [GitHub](https://github.com/bossrus/kostrovIA). Production собирается из ветки `main`. README содержит команды запуска и настройки статического хостинга. Сообщения работодателю в рамках этой правки не отправлялись.
